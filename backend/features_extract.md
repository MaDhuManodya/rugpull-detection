# Chapter 3
Rug pulls remain one of the most damaging categories of fraud in decentralized finance because the mechanisms that make blockchain systems attractive to users, namely permissionless deployment, pseudonymity, and the absence of a central authority, are the same mechanisms that shield malicious actors from scrutiny until an exploit has already occurred. A rug pull is rarely a single, isolated act. It is instead the final step of a sequence of coordinated on-chain behaviors that begins with contract deployment, continues through a period of liquidity accumulation and community building, and ends with the sudden withdrawal of funds or the manipulation of contract logic to prevent investors from selling their tokens. This sequential character is what makes the problem tractable from a machine learning perspective, but it is also what makes many existing detection approaches insufficient, since they treat the problem as a static classification task rather than as a process that unfolds over time across a network of interacting addresses.
The objective of this study is to design and implement a detection framework that identifies rug pulls before the liquidity withdrawal event takes place, using the structural relationships between wallets, contracts, and liquidity pools together with the temporal order in which those relationships form. Rather than examining a token in isolation, the proposed system represents each token ecosystem as an evolving graph in which nodes correspond to blockchain entities and edges correspond to transactions, and it learns to recognize the early structural and temporal signatures that precede a rug pull. The motivation for this framing follows from an observation that recurs throughout the literature examined in Chapter 2: rug pulls exhibit identifiable topological patterns, such as a small number of wallets funneling liquidity toward a single deployer address, or an unusually rapid concentration of token supply in accounts that later coordinate their exit, and these patterns are visible in the transaction graph well before the exploit is executed.
Three considerations shaped the design decisions behind this methodology. First, static graph models capture structure at a single point in time and therefore miss the evolution of suspicious behavior, which is why this study adopts a temporal graph learning approach rather than relying solely on a spatial graph neural network. Second, transaction data alone is an incomplete description of a token's risk profile, since two contracts with an identical transaction graph can carry very different risk if one contains an owner-only minting function and the other does not; this is the reason the proposed system fuses on-chain transactional signals with smart contract code-level signals rather than treating them as separate, unrelated inputs. Third, a model that produces a probability score without justification is of limited practical use to an auditor, an exchange listing team, or an individual investor who must decide whether to act on that score, which is why an explainability layer is treated as a core architectural component of the framework rather than an optional add-on applied after the fact.
The proposed methodology differs from the approaches surveyed in the literature review in three specific ways. Where prior graph-based detectors generally apply a single attention-based graph neural network to a static snapshot of the transaction graph, this study couples a Graph Attention Network v2 (GATv2) with a Temporal Graph Network (TGN) so that spatial structure and temporal evolution are learned jointly rather than being combined in a loosely connected pipeline. Where prior multimodal detectors typically concatenate feature vectors from different sources without an explicit fusion mechanism, this study introduces a dedicated fusion module that learns the relative contribution of each modality before the fused representation reaches the graph learning stage. Where prior explainable rug pull detectors have generally applied a single explanation method in isolation, this study combines SHAP and GNNExplainer so that feature-level and structure-level explanations reinforce one another, producing a more complete account of why a given transaction pattern was flagged. Taken together, these design choices are intended to push detection earlier in the token lifecycle, to make the resulting predictions auditable, and to keep the system general enough to apply across different blockchain networks and token standards rather than being narrowly tuned to a single dataset.
At the top of the pipeline, the blockchain network supplies the raw material for the entire study in the form of publicly recorded transactions, contract bytecode, and liquidity pool events. The data collection layer queries this raw material through node providers and block explorer application programming interfaces and stores it in a structured form suitable for downstream processing. The data preprocessing layer then cleans, deduplicates, and temporally orders these records, converting timestamps and raw values into a consistent representation that later stages can rely on without additional error handling.
From this cleaned dataset, the feature engineering layer derives four families of descriptive variables: on-chain features that summarize wallet and transaction behavior, smart contract features that summarize code-level risk indicators, graph features that summarize structural position within the transaction network, and temporal features that summarize the pace and rhythm of activity. Because these feature families originate from structurally different sources, ranging from numeric transaction statistics to categorical contract properties, they are not combined naively. Instead, the multimodal feature fusion layer learns a weighted combination that produces a single, unified representation for every node in the graph.
This fused representation becomes the input to the transaction graph construction stage, which assembles wallets, contracts, and liquidity pools into nodes and connects them with directed, timestamped edges that represent transfers, swaps, minting operations, and liquidity events. The resulting graph is passed to the Graph Attention Network v2 module, which learns spatial embeddings by attending over each node's neighborhood, and these spatially-aware embeddings are then passed to the Temporal Graph Network module, which updates a per-node memory state as new interactions arrive and produces embeddings that reflect both structure and history. The binary classification module reads the final embeddings and produces a rug pull probability for each token, and the explainability module attaches a SHAP-based feature attribution and a GNNExplainer-based subgraph explanation to every prediction that crosses the decision threshold, so that the final output of the system is not merely a label but a label accompanied by a defensible rationale.
Two properties of this architecture are worth highlighting because they distinguish it from a conventional feed-forward classification pipeline. First, information flows in both a spatial and a temporal direction: the GATv2 module aggregates information horizontally across a node's neighbors at a given point in time, while the TGN module aggregates information vertically across a node's own history through its memory state. Second, the explainability module is positioned as a terminal stage that consumes the same graph and feature representations used for prediction, rather than as a separate analysis performed after the fact on a black-box output; this ensures that the explanations are faithful to the exact representation the classifier used to reach its decision.

Transaction data forms the backbone of the transaction graph described in Section 3.7 and is collected at the level of individual events rather than aggregated summaries, since the temporal learning module described in Section 3.8 requires an ordered stream of discrete interactions rather than a pre-aggregated snapshot. For each transaction, the collection layer records the sender address, the receiver address, the transferred value, the associated gas expenditure, the block timestamp, and a reference to the invoked contract function where applicable. Wallet addresses encountered during this process are registered as nodes the first time they appear and are never discarded, even if a wallet interacts with a token only once, because a single, precisely timed transaction, such as a large withdrawal immediately following liquidity addition, can itself be a decisive signal.
Liquidity information is collected separately from ordinary transaction data because liquidity events carry a different semantic meaning: a liquidity addition establishes the tradability of a token, while a liquidity removal is often the terminal act of a rug pull. The collection layer therefore captures liquidity pool creation, the identities of addresses that supply liquidity, the timing and magnitude of additions and removals, and the resulting change in the pool's reserve ratio, since a sudden and asymmetric change in this ratio is one of the strongest empirical indicators of an exit event.

6. Feature Scaling / Normalization
Missing values arise most often in the smart contract feature category, since not every contract is verified and source-level metadata is therefore unavailable for a subset of tokens. Rather than imputing these values, which would risk fabricating a signal that does not exist, the preprocessing layer marks such fields with an explicit indicator variable, allowing the feature engineering layer described in Section 3.5 to treat an unverified contract as informative in its own right, since the decision not to verify a contract is itself correlated with elevated risk.
Temporal ordering is the step that gives the pipeline its sequential character. Every transaction, liquidity event, and contract interaction associated with a token is sorted by block timestamp into a single chronological stream, and this stream is what allows the framework to reconstruct, at any point in a token's history, the exact state of the graph as it existed at that moment, a property that is essential for the Temporal Graph Network described in Section 3.8 and for the early detection objective of the study as a whole. Graph construction then converts this ordered stream into the node and edge representation described in Section 3.7, and feature scaling applies min-max normalization to bounded numeric attributes and z-score standardization to unbounded ones, so that features measured in vastly different units, such as token value in wei and transaction counts, do not disproportionately influence the learning process purely because of their scale.

On-chain features describe how a token behaves from the perspective of ordinary transaction activity. Holder concentration, expressed as a Gini coefficient over token balances, is particularly informative because rug pulls are almost always preceded by a period in which a small number of wallets accumulate a disproportionate share of the supply, either through direct minting or through coordinated purchases; a rising Gini coefficient over a short window is treated as a leading indicator rather than a static descriptor. Smart contract features, by contrast, describe what a token's code permits rather than what has actually happened, and are included because behavioral history alone cannot capture risk that has not yet been exercised: a contract that grants its owner the ability to mint unlimited tokens or to pause transfers selectively carries elevated risk even during a period of otherwise normal trading activity.
Graph features quantify a node's position within the transaction network independently of any specific transaction value. Betweenness centrality identifies wallets that sit on many of the shortest paths between other wallets and the liquidity pool, a position that is disproportionately occupied by intermediary accounts used to obscure the origin of funds. The k-core index, which measures how deeply embedded a node is within a densely connected subgraph, is used to distinguish organically formed trading communities from artificially inflated wash-trading rings, since the latter tend to form unusually dense, self-referential cores. Temporal features complete the picture by describing the pacing of activity rather than its structure or content: the burstiness of transactions, defined as the coefficient of variation of inter-transaction time intervals, tends to spike sharply in the hours preceding a rug pull as the perpetrators rapidly execute a series of preparatory transactions before the final withdrawal.
Each of the four categories is computed at every discrete time step available in the temporally ordered stream established in Section 3.4, rather than once over the entire history of a token, which is what allows the framework to observe how a token's feature profile evolves and to detect the early stages of a developing rug pull rather than only its completed form.
3.6 Multimodal Feature Fusion
Multimodal fusion, in the context of this study, refers to the process of combining feature vectors that originate from structurally different sources, namely the on-chain, smart contract, graph, and temporal categories described in Section 3.5, into a single representation that a downstream neural network can consume. Fusion is necessary because these categories differ not only in scale but in statistical character: on-chain and temporal features are continuous and dense, smart contract features are largely categorical and sparse, and graph features depend on the surrounding network rather than on the node in isolation. Concatenating these vectors directly, as several of the multimodal approaches reviewed in Chapter 2 do, forces the downstream network to learn the relative importance of each modality implicitly and without guidance, which is both statistically inefficient and difficult to interpret.
The proposed framework instead adopts a gated attention-based fusion strategy. Each feature category is first projected independently into a common latent dimension through a category-specific linear transformation, which allows each modality to be represented in a comparable space without forcing them to share parameters prematurely. A learned gating vector then computes an attention weight for each of the four projected representations, conditioned on the node's overall feature profile, and the final fused representation is produced as the weighted sum of the four projections. This design allows the network to rely more heavily on smart contract features for a node whose contract exposes high-risk functions, while relying more heavily on temporal features for a node whose behavioral history is unusually bursty, rather than applying a fixed, dataset-wide weighting to every node regardless of its individual characteristics.
This strategy was selected over simple concatenation and over a fixed-weight averaging scheme for two reasons. First, the relative informativeness of each modality is not constant across tokens: for a verified, well-audited contract, smart contract features carry little discriminative signal and graph or temporal features become more important, whereas for an unverified contract, the reverse is often true. A learned, per-node gating mechanism accommodates this variability, while a fixed weighting cannot. Second, the gating weights themselves become a useful diagnostic output in their own right, since they indicate which modality drove a given fusion outcome and can be inspected alongside the explanations produced by the module described in Section 3.10.
The expected output of this stage is a single fused embedding vector for every node in the transaction graph, of fixed dimensionality regardless of how many features were available for that particular node, including cases where certain smart contract fields were marked as missing during preprocessing. This fused embedding is what is passed forward into the transaction graph construction stage described in Section 3.7, replacing the four separate feature families with one unified node representation.
The transaction graph is constructed as a directed, attributed, temporal multigraph. Three types of entities are represented as nodes: wallet addresses, smart contracts, and liquidity pool contracts, each carrying the fused feature vector produced in Section 3.6 as its initial node attribute. Edges represent discrete on-chain interactions and are directed from the initiating address to the receiving address, carrying the transaction timestamp, the transferred value, and a categorical label identifying the interaction type, such as transfer, swap, mint, liquidity addition, or liquidity removal. Because a single pair of nodes can interact more than once, and because the temporal ordering of those interactions is itself informative, the graph is represented as a multigraph in which repeated interactions between the same pair of nodes are preserved as separate, individually timestamped edges rather than being collapsed into a single aggregated edge.

Once the transaction graph has been constructed, spatial structure is learned using a Graph Attention Network v2. In this module, every node updates its representation by attending over the representations of its immediate neighbors, computing an attention coefficient for each neighbor that reflects how relevant that neighbor's current state is to the node being updated. Unlike the original graph attention formulation, in which the attention mechanism can only express a fixed ranking of neighbors regardless of the query node, the v2 formulation used here allows attention scores to depend jointly on both the source and the target node, which is important in this setting because the relative importance of a neighboring wallet is not fixed; a wallet that is unremarkable when queried from one contract may be highly relevant when queried from another, depending on the specific pattern of interaction between them.
GATv2 was selected over the original GAT formulation, over graph convolutional networks, and over GraphSAGE for three reasons specific to the requirements of this study. First, the dynamic attention property of GATv2, in which attention scores are not restricted to a fixed ranking, better matches the way that risk-relevant relationships in a transaction graph shift depending on which node is being evaluated, a property that a static-ranking attention mechanism cannot represent. Second, attention weights provide an intrinsic, per-edge measure of relevance that supports the structural explanations produced by GNNExplainer in Section 3.10, whereas convolutional aggregation schemes such as those used in graph convolutional networks apply a fixed, degree-normalized weighting that offers no comparable signal. Third, because the transaction graph in this study is heterogeneous, containing wallets, contracts, and liquidity pools with different feature distributions, an attention-based aggregation is better suited than a uniform or sampling-based aggregation scheme to down-weighting neighbors whose feature profile is uninformative for a given node, which GATv2 achieves without requiring a fixed sampling budget per node.
For completeness, the update performed by a single GATv2 layer for node i can be stated formally. Given the fused feature vector h_i produced in Section 3.6 and a learnable weight matrix W, an unnormalized attention score for a neighbor j in N(i) is computed as e(h_i, h_j) = a^T LeakyReLU(W [h_i || h_j]), where a is a learnable scoring vector and [ || ] denotes concatenation. Crucially, because the linear transformation W is applied to the concatenated pair before the nonlinearity, rather than being applied separately to h_i and h_j before an additive combination as in the original GAT formulation, the resulting score can express any ranking over neighbors depending on the query node, which is the defining property of the v2 formulation referenced in Section 3.7.2. Normalized attention coefficients are then obtained as alpha_ij = softmax_j(e(h_i, h_j)) over the neighborhood N(i), and the updated node representation is h_i' = sigma( sum over j in N(i) of alpha_ij · W h_j ), where sigma is a nonlinear activation. With K attention heads, the per-head outputs are concatenated, and a final linear projection maps the concatenated result back to the model's working dimension before the representation is passed to the temporal module described in Section 3.8.
The spatial embeddings produced by the GATv2 module in Section 3.7 describe a node's position within its neighborhood at a single point in time, but they do not, by themselves, capture how a node's behavior changes across the sequence of events that make up its history. This limitation is addressed by a Temporal Graph Network, which maintains a persistent memory state for every node and updates that memory continuously as new interactions arrive, allowing the framework to represent a node not as a static point but as an evolving trajectory.
Figure 3.3: Temporal Graph Network module showing the message function, time encoding, memory update, and embedding update stages
As illustrated in Figure 3.3, each interaction event involving a pair of nodes u and v at time t triggers a message function, which computes a message summarizing the interaction from the perspective of each participant, using the current memory states of u and v together with the edge attributes of the event itself, such as the transaction type and transferred value. This message is combined with a time encoding, a learned function that converts the raw timestamp, or more precisely the elapsed time since the node's previous event, into a continuous vector representation, which allows the network to distinguish between interactions that are closely spaced in time and interactions that are separated by long, quiet intervals, a distinction that is directly relevant to detecting the bursts of activity associated with an impending rug pull.
The combined message and time encoding are used to update the node's memory state, which is implemented as a recurrent update function so that the memory reflects a compressed summary of the node's entire interaction history rather than only its most recent event. This memory state is then read out, together with the spatial embedding produced by GATv2, to compute the node's final temporal embedding at time t, which is the representation ultimately consumed by the binary classification module described in Section 3.9. Because memory updates occur continuously as new events arrive rather than only at fixed, aggregated intervals, the framework is able to compute a rug pull risk score at any point in a token's history, including points well before liquidity has actually been withdrawn, which is what allows the system to support early rather than retrospective detection.
The Temporal Graph Network was selected over static graph snapshot approaches and over simpler recurrent baselines for two principal reasons. First, snapshot-based methods, which discretize a token's history into fixed time windows and treat each window as an independent graph, discard the fine-grained ordering of events within a window and require the analyst to choose a window size in advance, a choice that is difficult to make correctly given how widely the pace of activity varies across different rug pull schemes. The continuous, event-driven memory update used by TGN removes this dependency on a fixed window size entirely. Second, because TGN maintains memory per node rather than per graph, it naturally supports the entity-centric graph representation adopted in Section 3.7.1, allowing a wallet's memory to persist and continue to update even as it interacts with new contracts and new counterparties over time, which is essential in a domain where the same set of wallets frequently reappears across multiple rug pull schemes.
Stated formally, when an interaction event (u, v, t, e_uv) occurs, where e_uv denotes the raw edge attributes such as transaction type and value, a message for node u is computed as m_u(t) = MSG( s_u(t-), s_v(t-), phi(t - t_u_prev), e_uv ), where s_u(t-) and s_v(t-) denote the memory states of u and v immediately before the event, phi is the time encoding function referenced in Section 3.8, and t_u_prev is the timestamp of node u's previous event; a symmetric message m_v(t) is computed for node v. The memory state is then updated through a recurrent function, s_u(t) = MEM( s_u(t-), m_u(t) ), implemented in this study as a gated recurrent unit, which allows the memory to retain long-range dependencies from early in a token's history, such as an initial round of concentrated minting, while still being sensitive to sudden recent changes, such as a burst of withdrawals. The final temporal embedding used for downstream classification is z_u(t) = EMB( s_u(t), h_u'(t) ), a combination of the updated memory state and the spatial embedding h_u' produced by the GATv2 module in Section 3.7, so that the representation passed to the classification module in Section 3.9 reflects both where a node sits in the graph and how it has behaved over time.
The time encoding function phi deserves particular attention because it is what allows the module to distinguish rapid, bursty activity from slow, steady activity without being told explicitly to do so. Following the functional time encoding approach adopted in this study, phi maps a scalar time difference to a vector of sinusoidal features at multiple learned frequencies, in a manner structurally similar to positional encoding in sequence models, which gives the network a continuous and differentiable representation of elapsed time rather than a discretized one. This continuous representation is what allows the memory update to respond proportionally to a ten-minute gap between transactions and a ten-hour gap between transactions, rather than collapsing both into the same coarse time bucket, a distinction that is often decisive when identifying the compressed sequence of actions that precedes a rug pull.

Negative sampling is also addressed at this stage, since the population of legitimate tokens vastly exceeds the population of confirmed rug pulls and presenting the classifier with every legitimate example in every epoch would further entrench the class imbalance discussed above beyond what the class-weighted loss alone can compensate for. Legitimate tokens are therefore sampled per epoch such that the effective ratio of legitimate to rug pull examples seen by the network remains within a fixed band, while the full set of confirmed rug pulls is retained in every epoch, ensuring that the comparatively rare positive class is never under-represented during training regardless of how the negative sampling is configured.
A prediction from the classification module described in Section 3.9 is only as useful as the confidence a reviewer can place in it, and confidence in a machine-generated fraud flag is difficult to establish without an accompanying explanation. The explainability module therefore attaches two complementary forms of explanation to every prediction that crosses the decision threshold: a feature-level explanation produced by SHAP and a structure-level explanation produced by GNNExplainer.
3.10.1 SHAP-based Feature Explanation
SHAP is applied to the fused feature representation described in Section 3.6, treating the trained classification pipeline as the function to be explained and computing, for each prediction, the contribution of every individual feature to the deviation of that prediction from the model's average output. This produces a local explanation for each flagged token, identifying, for example, that an unusually high holder concentration and the presence of an owner-only mint function were the two largest contributors to a particular token being flagged, expressed in a common unit that allows features from different categories, such as on-chain, smart contract, graph, and temporal features, to be directly compared against one another despite originating from structurally different sources. Aggregating these local explanations across the full set of flagged tokens in the test set also yields a global explanation, summarizing which feature categories tend to drive positive predictions across the dataset as a whole, which is useful both for validating that the model has learned domain-relevant signals rather than spurious correlations and for guiding future feature engineering efforts.
Where SHAP explains a prediction in terms of feature values, GNNExplainer explains a prediction in terms of graph structure, identifying the minimal subgraph and the minimal subset of node features that are jointly sufficient to reproduce the classification module's prediction for a given token. In practice, this is achieved by learning a soft mask over the edges and node features of the token's local transaction graph, optimized so that passing only the masked subgraph and masked features through the trained GATv2 and TGN modules reproduces, as closely as possible, the original prediction, while keeping the mask itself as sparse as possible so that the resulting explanation remains human-readable. The output of this process is a compact explanatory subgraph, typically consisting of a small number of wallets and edges, together with an importance score for each retained edge and node, that shows a reviewer precisely which transactions and which counterparties the model relied on most heavily when producing its prediction.
SHAP and GNNExplainer are combined rather than used in isolation because they answer two related but distinct questions, and neither is sufficient on its own to fully justify a rug pull flag. SHAP identifies which computed features mattered, but it cannot, by itself, indicate which specific wallets or transactions gave rise to those feature values, since features such as holder concentration or clustering coefficient are aggregate quantities computed over the entire local neighborhood of a node. GNNExplainer identifies which specific wallets and transactions mattered, but it does not, by itself, translate that structural finding into the same feature vocabulary that a reviewer trained on the on-chain and smart contract feature categories from Section 3.5 would use to reason about risk. Presenting both explanations together allows a reviewer to move from a high-level feature-based summary, such as elevated holder concentration, to the exact subgraph responsible for it, such as three wallets that received tokens directly from the deployer within a narrow time window, closing the gap between an abstract risk score and a concrete, auditable chain of evidence.
Five metrics are used to evaluate the classification module described in Section 3.9, each capturing a different aspect of performance that is individually necessary but not, on its own, sufficient to characterize a detector operating on an imbalanced dataset. Accuracy reports the overall proportion of correctly classified tokens but is included primarily as a baseline reference rather than a primary metric, since accuracy alone can be misleadingly high on an imbalanced dataset dominated by legitimate tokens. Precision reports the proportion of tokens flagged as rug pulls that are genuinely rug pulls, which matters because a high false positive rate would erode trust in the system among the auditors or exchanges expected to act on its output. Recall reports the proportion of actual rug pulls that the system successfully flags, which is treated as the single most important metric in this study given the asymmetric cost structure discussed in Section 3.9, since a missed rug pull represents a direct and often unrecoverable financial loss to investors. The F1-score, the harmonic mean of precision and recall, is reported to summarize the trade-off between these two metrics in a single value, and the area under the receiver operating characteristic curve (ROC-AUC) is reported to characterize the classifier's discriminative ability across all possible decision thresholds, independent of the specific threshold selected in Section 3.9.

Performance is additionally reported as a function of detection lead time, defined as the interval between the moment the system first flags a token and the moment the actual liquidity withdrawal event occurs, since a model that only detects a rug pull after it has effectively already happened does not satisfy the early detection objective stated in Section 3.1, regardless of how favorably it scores on the five metrics above. Finally, the proposed framework is compared against three categories of baseline: a feature-based classifier that uses the on-chain and smart contract features from Section 3.5 without any graph structure, a static graph neural network that uses GATv2 on a single aggregated snapshot of each token's transaction history without temporal modeling, and a temporal-only baseline that uses TGN without the spatial attention provided by GATv2. This ablation-style comparison is intended to isolate the contribution of each architectural component described in Sections 3.6 through 3.8, rather than only comparing the full system against unrelated prior work.
The methodology described in this chapter is expected to yield four principal benefits, each following directly from a specific design decision made earlier in the chapter. First, by combining spatial attention with continuous temporal memory, the framework is expected to achieve meaningfully longer detection lead times than approaches that rely on a single static graph snapshot, since it is able to update its risk assessment continuously as new transactions arrive rather than waiting for a discrete evaluation window to close. Second, by attaching a dual SHAP and GNNExplainer explanation to every positive prediction, the framework is expected to produce outputs that are directly usable by human reviewers, such as exchange listing teams or independent auditors, without requiring those reviewers to trust an opaque probability score in isolation.
Third, because the multimodal fusion strategy described in Section 3.6 learns per-node modality weights rather than a fixed, dataset-wide weighting, the framework is expected to generalize more robustly across tokens with differing data availability, such as tokens with unverified contracts or comparatively short transaction histories, than approaches that assume a uniform feature profile across the dataset. Fourth, because the graph representation adopted in Section 3.7.1 is entity-centric and the collection layer described in Section 3.3 is built against the shared conventions of Ethereum Virtual Machine compatible networks, the framework is expected to transfer with limited modification to other chains that share this format, which is a practical consideration given how frequently rug pull schemes are executed on newer or less-scrutinized networks precisely because established detection tools have not yet been adapted to them.
From a practical standpoint, the framework described in this chapter is intended to support three concrete use cases: a pre-listing screening tool that decentralized exchanges could apply before allowing a new token to be traded, a continuous monitoring service that surfaces early warnings to investors already holding a given token, and an investigative aid for blockchain analytics firms and regulators seeking to reconstruct the sequence of events behind a completed rug pull. Each of these use cases benefits differently from the properties emphasized in this methodology: pre-listing screening depends most heavily on the early detection lead time discussed above, continuous monitoring depends most heavily on the framework's ability to update its assessment as new data arrives, and investigative use depends most heavily on the structural explanations produced in Section 3.10.
This chapter presented the research methodology developed for the early detection of rug pulls in blockchain-based token ecosystems. The proposed framework was described as an eleven-stage pipeline beginning with raw blockchain data collection and preprocessing, proceeding through feature engineering across four distinct categories, and combining those categories through a learned multimodal fusion mechanism. The fused node representations were shown to be organized into an entity-centric transaction graph, over which a Graph Attention Network v2 learns spatial structure and a Temporal Graph Network learns temporal evolution through a continuously updated per-node memory. A binary classification module was described that converts the resulting temporal embeddings into a calibrated rug pull probability, trained with a class-weighted loss and evaluated against a threshold chosen to reflect the asymmetric cost of missed detections. An explainability module combining SHAP and GNNExplainer was presented as a core rather than auxiliary component, providing both feature-level and structure-level justification for every flagged token.
The evaluation strategy described in this chapter emphasized a chronological rather than random data split, a set of five complementary classification metrics together with a dedicated measure of detection lead time, and a comparison against feature-based, spatial-only, and temporal-only baselines intended to isolate the contribution of each architectural component. The expected outcomes discussed in the final section of this chapter tied each of these design decisions back to a specific practical benefit, namely earlier detection, more auditable predictions, more robust generalization across tokens with varying data availability, and portability across blockchain networks that share a common transaction format. Chapter 4 builds directly on the methodology established here, presenting the implementation details, the specific datasets used, and the empirical results obtained when the framework described in this chapter is applied in practice.


# Chapter 4
The preceding chapters established the conceptual and empirical foundations of this research. Chapter Two situated early rug pull detection within the wider literature on blockchain fraud, graph representation learning and temporal modelling, while Chapter Three set out the research methodology, including the design rationale, the datasets to be used, the evaluation protocol and the hypotheses under investigation. This chapter moves from justification to construction. Its purpose is to describe, in sufficient technical detail for the work to be reproduced, how the methodology defined in Chapter Three is realised as a working research prototype.
The chapter is organised so that it mirrors the logical path a unit of blockchain data takes through the system: from its origin on a public ledger, through collection and storage, through cleaning and feature construction, through graph and temporal representation learning, to a final classification decision that is accompanied by a human-readable explanation. Each subsequent section corresponds to one stage of this pipeline. Section 4.2 introduces the system as a whole and explains how its components interact; Sections 4.3 to 4.9 describe the data-facing layers of the system, namely component design, data collection, database design, preprocessing and feature engineering, culminating in the construction of the transaction graph that is passed to the learning components; Sections 4.10 to 4.13 describe the learning core of the system, namely the graph attention layer, the temporal memory layer, the classification head and the explainability layer; and Sections 4.14 to 4.18 describe the surrounding engineering concerns of dashboard design, deployment, technology selection, algorithmic summary and computational complexity. Section 4.19 closes the chapter with a short summary that links the implementation back to the objectives stated in Chapter One.
The prototype is organised as a layered, pipeline-oriented architecture in which each layer consumes the output of the layer beneath it and exposes a well-defined interface to the layer above it. This layering serves two purposes. First, it keeps the concerns of data acquisition, data engineering, representation learning and decision-making separate, which simplifies testing, since each layer can be validated in isolation before the pipeline is assembled end-to-end. Second, it mirrors the natural life cycle of a token on a decentralised exchange — deployment, early trading activity, liquidity provision, and either continued operation or abrupt abandonment — so that the architecture itself provides a map of where in that life cycle a given piece of evidence originates.
Figure 4.1 shows the eleven layers of the architecture and the direction of data flow between them. Raw ledger data enters at the top, through the Blockchain Network layer, and is progressively transformed as it descends through collection, cleaning, feature construction, fusion and graph construction, before being consumed by the two learning components — the spatial encoder (GATv2) and the temporal encoder (TGN) — and finally converted into a classification decision that is accompanied by an explanation.
Two properties of this architecture are worth highlighting before the individual layers are discussed in detail. First, the pipeline is designed to operate incrementally rather than in a single batch pass. Because a rug pull is, by definition, a rapid change in on-chain behaviour, the system is built to re-evaluate a token's risk score every time new transaction, liquidity or contract-interaction data becomes available for it, rather than only at fixed intervals. Second, the two learning components are deliberately kept distinct rather than fused into a single monolithic model. The Graph Attention Network v2 (GATv2) layer is responsible for spatial reasoning — understanding a token's position within the wider graph of wallets, contracts and liquidity pools at a given instant — while the Temporal Graph Network (TGN) layer is responsible for reasoning about how that position evolves over time. Separating these concerns allows each component to be trained, tuned and, where necessary, replaced independently, and it allows the explainability layer described in Section 4.13 to attribute a prediction to either structural or temporal evidence, which is informative for an analyst deciding how urgently to act on an alert.

A collector microservice subscribes to new blocks as they are mined and extracts every transaction whose ‘to’ address matches a token contract, a decentralised exchange router, or a liquidity pool already known to the system. Each transaction is decomposed into sender, receiver, value, gas used and calldata, and the calldata is decoded, where the function signature is recognised, to determine whether the transaction represents a transfer, an approval, a swap, or a liquidity operation. Wallet records are created or updated for every address encountered, and contract records are created for every address that contains bytecode, with the compiler metadata and constructor arguments recorded where a verified source is available.
Liquidity events are treated as a first-class category rather than as ordinary transactions, because the addition and, in particular, the removal of liquidity are the events most directly implicated in a rug pull. A dedicated listener decodes the Mint, Burn and Swap events emitted by automated market maker pools, and records the direction, magnitude and counterparties of each event, together with the resulting change in the pool's reserve ratio.
Figure 4.2 shows how these sources feed into a common collection workflow. Node, explorer and mempool sources are polled or subscribed to by a pool of asynchronous collector workers; extracted records are placed on a message queue that provides buffering and automatic retry in the event of a downstream failure; a validation and deduplication stage removes malformed or duplicate records before they are written to staging tables in PostgreSQL, from which the feature engineering layer reads.
The storage layer uses a normalised relational schema in PostgreSQL rather than a document store, principally because the relationships between tokens, wallets, contracts and transactions are themselves part of the signal the system is trying to model, and a relational schema with explicit foreign keys makes those relationships queryable and consistent. PostgreSQL was also chosen for its mature support for indexing on composite keys and timestamp ranges, both of which are used heavily by the feature engineering layer.

The Tokens table is the anchor of the schema: nearly every other table carries a token_id foreign key, since the unit of analysis and the unit of prediction is a token rather than an individual wallet or transaction. The Predictions table is deliberately append-only — a new row is written each time the model re-scores a token rather than overwriting the previous score — so that the risk trajectory of a token can be reconstructed and plotted on the dashboard described in Section 4.14. Composite indexes are defined on (token_id, block_timestamp) for the Transactions and Liquidity tables, since almost every downstream query filters by token and orders by time.
Raw collected data cannot be passed directly to the feature engineering layer, both because blockchain data collection is inherently subject to duplication and reordering, and because the numerical ranges of on-chain quantities such as token value or gas price vary by many orders of magnitude across tokens. The preprocessing pipeline addresses six concerns.
Cleaning: transactions with malformed calldata, zero-address artefacts, or values that cannot be decoded against a known ABI are flagged and excluded from feature computation, though they are retained in raw form for auditability.
Timestamp ordering: transactions within a block do not always arrive at the collector in execution order; records are re-ordered by block number and transaction index before being handed to any component that is sensitive to sequence, in particular the temporal learning layer.
Missing value handling: fields that cannot be resolved at collection time, such as the source-verification status of a contract, are stored as explicit nulls rather than sentinel values, and downstream feature computation applies documented imputation rules rather than silently defaulting to zero.
Feature scaling: monetary and count-based features are highly right-skewed, so continuous features are log-transformed and then standardised using statistics computed on the training partition only, which avoids leaking test-set distributional information into the scaling parameters.
4.7 Feature Engineering
Feature engineering converts cleaned, structured records into the numerical representations consumed by the fusion and graph-construction stages. Features are organised into four groups, each targeting a different aspect of rug-pull behaviour identified in the literature review.
4.7.1 On-chain Features
On-chain features are computed directly from transaction and wallet records and capture coarse trading and distribution statistics: total and unique-wallet transaction counts, buy-to-sell ratio, the Gini coefficient of token holdings across wallets, the proportion of supply held by the creator address, and the time elapsed since contract deployment. These features are inexpensive to compute and provide a fast baseline signal that does not depend on the graph or temporal components being available.
4.7.2 Smart Contract Features
Contract-level features are derived from bytecode and, where available, verified source code: the presence of owner-only functions capable of minting new supply, pausing transfers, or altering trading fees; the presence of a proxy pattern that would allow the contract's logic to be replaced after deployment; whether liquidity has been locked or the pool's LP tokens burned; and whether the contract has passed automated static-analysis checks for known rug-pull-enabling patterns such as hidden mint functions or blacklist mechanisms.
4.7.3 Graph Features
Graph features summarise a token's position within its transaction graph before that graph is passed to the GATv2 layer: node degree and weighted degree for the token's central contract and pool nodes, local clustering coefficient, the number of distinct wallet clusters interacting with the token, and the concentration of edge weight on the small number of wallets that first supplied liquidity. These features act partly as a sanity check against the learned graph embeddings and partly as auxiliary inputs to the fusion layer.
4.7.4 Temporal Features
Temporal features summarise how the above quantities change over short, rolling windows: the rate of change in unique-buyer count over the preceding hour, the acceleration of liquidity withdrawal relative to liquidity addition, and the inter-event time between successive large transactions. These features are designed to be sensitive to the abrupt behavioural discontinuities — a sudden concentration of sell transactions, or a sharp drop in pool reserves — that precede most rug pulls, and they form the raw event stream consumed by the TGN memory module described in Section 4.11.
4.8 Multimodal Feature Fusion
The three feature groups described in Section 4.7 — tabular on-chain and contract features, textual contract metadata, and graph-structural features — are heterogeneous in both type and dimensionality, and the multimodal machine learning literature reviewed in Chapter Two motivates combining them through an explicit fusion stage rather than concatenating them naively.
Figure 4.4 shows the fusion workflow. Each modality is first passed through a modality-specific encoder: tabular on-chain and contract features are encoded with a small feed-forward network; contract source and metadata text is encoded with a pretrained sentence embedding model that is fine-tuned on a held-out sample of labelled contracts; and graph-structural summary statistics are encoded with a second feed-forward network. The three resulting fixed-length vectors are then combined by a hybrid fusion layer.
Figure 4.4: Multimodal feature fusion workflow, from modality-specific encoders through attention-weighted hybrid fusion to a unified token representation.
A hybrid fusion strategy is used in preference to pure early or pure late fusion. Pure early fusion, in which raw features from all modalities are concatenated before any modality-specific processing, was found in preliminary experimentation to allow the high-dimensional tabular features to dominate the smaller textual and graph-summary vectors. Pure late fusion, in which each modality is scored independently and the scores averaged, discards cross-modal interactions that are informative in practice — for example, the combination of an unverified contract with a very young deployment timestamp is more suspicious than either feature alone. The hybrid strategy adopted here first encodes each modality independently, preserving modality-specific structure, and then combines the encoded vectors with a learned attention weighting, so that the fusion layer can down-weight a modality when it is missing or uninformative for a particular token, rather than being forced to average in a constant, non-adaptive way.
The output of the fusion layer is a fixed-length unified token representation vector that is used in two places downstream: as the initial node feature for the token's contract node when the transaction graph is constructed (Section 4.9), and as an auxiliary input concatenated with the GATv2/TGN embeddings immediately before classification (Section 4.12). Providing the fused representation at both points allows the graph and temporal components to refine a token-level prior rather than having to reconstruct token-level context purely from local neighbourhood structure.
A node is created for every wallet and every contract address that has interacted with the token, with the token's own contract and its primary liquidity pool distinguished as designated hub nodes because a disproportionate share of edges is incident to them. A directed edge is created from a sender to a receiver for every transfer, swap or liquidity operation, with the edge weight set to a monotonic transformation of the transaction's value, so that large transfers are not simply present or absent in the graph but contribute proportionally more to the attention computation described in Section 4.10.
The graph is directed because the direction of value flow is informative — a wallet that only ever receives from the liquidity pool and never sends back to it behaves differently from one that cycles funds through the pool repeatedly — and weighted for the reason given above. Critically, the graph is also dynamic: rather than representing a token's history as a single static graph, each edge additionally carries the timestamp of the event it represents, so that the same pair of nodes can be connected by multiple, differently weighted edges at different points in time. This time-stamped edge list is the structure passed to the temporal learning layer in Section 4.11, while a windowed, time-aggregated snapshot of the same graph is what GATv2 consumes at each evaluation point.
Each GATv2 layer computes an attention coefficient for every edge in a node's local neighbourhood by concatenating the source and target node features, applying a shared linear transformation and a LeakyReLU non-linearity, and then scoring the result with a learned attention vector, following the layer-wise process illustrated in Figure 4.6. Multiple attention heads are computed in parallel, each with independently learned parameters, so that different heads can specialise in different relational patterns — for example, one head may learn to weight liquidity-removal edges heavily while another specialises in ordinary transfer volume.
The input to the graph learning module is the windowed transaction graph produced in Section 4.9, together with the initial node features drawn from the fused token representation (Section 4.8) for hub nodes and from lightweight wallet-level statistics for ordinary wallet nodes. Two stacked GATv2 layers are used, with the outputs of the multiple attention heads in the first layer concatenated and the outputs of the second layer averaged, following common practice for the final layer of a multi-head attention stack. The output of the module is a spatially contextualised embedding for every node in the graph, with particular emphasis placed on the embeddings of the token contract and liquidity-pool hub nodes, since these are the embeddings carried forward into classification.
The temporal component is a Temporal Graph Network (TGN), which maintains a per-node memory vector that is updated every time the node is involved in a new interaction, allowing the model to reason about a token's evolving behaviour rather than only its behaviour at a single evaluation instant.
Figure 4.7 shows the four-stage workflow executed for every interaction event. When an event involving nodes i and j at time t is observed, a message function combines the previous memory states of i and j, the time elapsed since each node's memory was last updated, and any features associated with the event itself, to produce a message vector. This message is passed to a memory updater, implemented as a gated recurrent unit, which produces the new memory state for the node. The updated memory is written back to a persistent per-node memory store, so that it is available as the starting point the next time that node is involved in an event, however long the intervening gap.
Figure 4.7: Temporal Graph Network workflow, from an interaction event through the message and memory-update functions to a time-aware node embedding.
A node's final embedding at evaluation time is not read directly from memory, but is instead computed by a temporal graph attention layer that combines the node's current memory with the memories of its recent temporal neighbours, which allows the embedding to reflect both the node's own history and the current behaviour of nodes it interacts with. This time-aware embedding for the token's hub nodes is what is concatenated with the corresponding GATv2 spatial embedding before classification, so that the classifier receives both a snapshot of current graph structure and a running summary of how that structure has been changing.
During training, the model minimises a class-weighted binary cross-entropy loss, with the class weight set to counteract the substantial imbalance between legitimate tokens and confirmed rug pulls in the labelled dataset described in Chapter Three. The decision threshold applied to the output probability is not fixed at the conventional 0.5, but is instead selected on a held-out validation partition to maximise recall on the rug-pull class subject to a precision floor, reflecting the asymmetric cost of a missed detection relative to a false alarm in this application. At inference time, the trained model is re-run for a token whenever sufficient new graph or temporal evidence has accumulated, and the resulting probability, together with the applied threshold, is written to the Predictions table described in Section 4.5, from where it is served to the dashboard and API.
A risk score alone is of limited practical value to an analyst who must decide whether to act on it; the system therefore pairs every prediction with an explanation, generated by combining two complementary techniques.
4.13.1 SHAP: Feature Importance
SHapley Additive exPlanations (SHAP) is applied to the fused feature vector and to the auxiliary on-chain, contract and graph-summary features that enter the classifier, producing an attribution of the predicted probability to each individual input feature. SHAP is used to generate two views: a local explanation for a single token, listing the specific features that most increased or decreased its risk score, and a global explanation, aggregated across many predictions, that summarises which categories of feature are most consistently associated with rug-pull predictions across the dataset as a whole. The local view is surfaced on the dashboard alongside each alert; the global view is used during model development and validation to check that the classifier is relying on plausible evidence rather than on spurious correlations.
SHAP treats the fused feature vector as an opaque set of inputs and cannot, on its own, explain which specific counterparties or interactions within the transaction graph drove a prediction. GNNExplainer is therefore applied to the GATv2 component to identify the minimal subgraph — the smallest set of nodes and edges — whose presence is sufficient to reproduce the model's prediction, together with an importance score for each node and edge in that subgraph. This produces exactly the kind of evidence an analyst needs to investigate a token manually: for example, that a small number of wallets funded directly by the deployer account for the majority of buy pressure shortly before a large liquidity withdrawal.
SHAP and GNNExplainer are combined rather than used in isolation because they answer different questions: SHAP answers which features mattered, while GNNExplainer answers which parts of the graph mattered. Presenting both together allows an analyst to move from a feature-level summary, such as an unusually high liquidity-withdrawal acceleration, to the specific subgraph — the specific wallets and pool interactions — responsible for that feature value, closing the gap between an automated risk score and an actionable investigative lead.
4.14.1 Overview / Risk Score Screen
The landing screen lists monitored tokens ranked by current risk score, with each entry showing the token symbol, its most recent predicted probability, the applied binary decision, and a sparkline of how its risk score has changed over the preceding period. This view is intended to answer the analyst's first question — which tokens deserve attention right now — as quickly as possible.
Selecting a token opens a detail screen showing the full prediction record: the current probability and label, the decision threshold in force at prediction time, the model version used, and the timestamp of the underlying evidence. This screen is the entry point to the explanation and graph views described next.
The explanation screen presents the SHAP local explanation for the selected token as a ranked bar chart of feature contributions, alongside a short natural-language summary generated from the top contributing features. This is the screen in which the feature-level output of Section 4.13.1 is made legible to a non-technical user.
The final screen renders the GNNExplainer subgraph for the selected token as an interactive node-link diagram, styled in the same manner as Figure 4.5, with edge thickness proportional to GNNExplainer's importance score, so that an analyst can visually trace the wallets and pool interactions responsible for the prediction. A history panel beneath the graph lists prior predictions for the same token, allowing the analyst to see how the risk score evolved as new evidence arrived.
The trained GATv2, TGN, fusion and classifier components are wrapped in a single inference service exposed through FastAPI, chosen for its asynchronous request handling, which suits the mixture of fast cached reads and slower on-demand graph re-computation the service must support, and for its automatic generation of an OpenAPI schema, which was used directly to build the dashboard's data-fetching layer.

4.18.1 Time Complexity
For a single token evaluated over a windowed transaction graph with n nodes and m edges, a single GATv2 layer with H attention heads has time complexity O(H · (n·d + m·d)) for node feature dimension d, since the attention coefficient for each edge is computed independently and node-wise transformations are linear in n. With two stacked layers this remains linear in the size of the token's local graph, which is bounded in practice by capping the number of temporal neighbours considered per node, as is standard for TGN-style architectures. The TGN component processes the event stream once per evaluation, giving a further O(m) contribution for message computation and memory updates. The classifier and fusion components operate on fixed-length vectors and contribute constant-time overhead per token. The dominant cost in practice is therefore linear in the number of edges in a token's windowed graph, which is why the graph is windowed rather than allowed to grow without bound across a token's entire history.
This chapter has described the practical implementation of the early rug pull detection system whose design was motivated in Chapter Two and whose methodology was specified in Chapter Three. Starting from raw blockchain data, the system was shown to collect, validate and store transaction, wallet, contract and liquidity records in a normalised PostgreSQL schema; to derive on-chain, contract, graph and temporal features from those records; to combine those features through a hybrid multimodal fusion layer; to represent each token as a directed, weighted, dynamic transaction graph; to learn spatial structure over that graph using GATv2 and temporal evolution using a TGN memory module; to classify the resulting representation with a lightweight MLP head calibrated to an operating threshold appropriate for an imbalanced, asymmetric-cost detection task; and to accompany every prediction with a combined SHAP and GNNExplainer explanation, surfaced through a dashboard and a FastAPI service.
